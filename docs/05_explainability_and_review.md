# 05 – Explainability and Human-in-the-Loop Review

Code: `src/plotting.py` (heatmaps), `app/review_app.py` (operator screen)

## 1. Heatmaps
Every rejected part comes with an anomaly map: red = patches unlike anything in the
memory bank of good parts. Figures generated by the pipeline:
- `reports/figures/heatmap_examples.png`: one example per defect type, with the true defect
  mask for comparison
- `reports/figures/missed_defects.png`: defects scored below the threshold (if any)
- `reports/figures/false_rejects.png`: good parts scored above the threshold (if any)

Looking at the misses and false rejects is the most valuable step: it shows *why* the model
fails, e.g. very small defects, or harmless variation like lighting reflections.

## 2. Why a human stays in the loop
- Anomaly detection says "unusual", not "defective". Harmless variation (dust, a reflection,
  a new batch of raw material) can look unusual too.
- The cost of a missed defect is high, so the threshold is set low: some good parts will be
  rejected. A quick human check is cheaper than scrapping them.
- Every operator decision is logged (`reports/review_log.csv`). The **overrule rate** is a key
  health metric: if operators overrule the AI more often over time, the line has changed and
  the memory bank should be refreshed.

## 3. The review screen
`streamlit run app/review_app.py`
- **Review queue:** parts the AI rejected, highest score first
- Camera image next to the heatmap, score vs. threshold, PASS / REJECT
- Buttons: **Confirm defect** / **Part is OK**, with an optional note
- Log of all decisions with the overrule rate
- Upload any image to test the model on new parts
